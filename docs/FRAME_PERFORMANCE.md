# 이동 중 프레임 진단 — 2026-09-28

## 22FPS 보고 후 추가 경량화

- 22FPS는 평균 약 45.5ms/프레임이며, 30FPS에는 33.3ms 이하가 필요하다. 최저 FPS 목표 달성 여부는 실제 이동 구간의 재측정이 필요하다.
- 전체 화면 후처리의 텍스처 읽기를 픽셀당 30회에서 13회로 줄였다. 중앙 샘플을 재사용하고 블룸을 3×3 가중 커널로 바꿨다. 밝기 정규화·색 보정·비네트·가장자리 보정은 유지하지만 블룸 모양은 근사치다.
- 부드러운 타원은 40분할에서 24분할로 변경했다. 튜토리얼 방향 그림자는 5겹에서 3겹으로 줄이고 알파를 보정했다. 접지 그림자를 포함한 객체당 정점 수는 720개에서 288개로 줄었다. 그림자의 겹침 모양과 윤곽은 약간 달라질 수 있다.
- 변경 후 전체 C++ 컴파일·링크와 diff 검사는 통과했다. GLSL 실행과 게임 FPS는 측정하지 않았다. 텍스처 읽기/정점 감소율을 전체 FPS 개선율로 해석하지 않는다.
- 추가 진단에는 22FPS가 나오는 빌드 구성과 창 제목의 update/draw/present 값이 필요하다. Debug와 Release 수치는 별도로 비교한다.

## 확인한 비용과 변경

- 튜토리얼의 기존 나무 충돌 검사는 이동 시마다 전체 나무를 순회하며 거리의 제곱근을 계산했다. 플레이어와 동물, 프레임 내 충돌 세부 단계마다 반복되는 비용이다.
- 나무 위치를 프레임 시작에 8×8 월드 단위 격자로 수집하고, 충돌 반경 0.6과 겹치는 셀만 검사하도록 변경했다. Actor 위치에서 매번 다시 수집하므로 프레임 사이의 부모/나무 위치 변경도 반영한다. 프레임의 충돌 단계 도중 지형을 이동하는 기능은 현재 없다.
- 격자 셀 메모리는 재사용하며 거리 비교에는 제곱 거리를 사용한다. 집·호수·유적 충돌 규칙과 첫 사냥터의 기존 충돌 격자는 유지한다.
- HUD 문자 출력은 문자마다 glCallList를 호출하는 대신 문자열의 목록을 glCallLists 한 번으로 제출한다. 글꼴과 문자 캐시는 유지한다.

## 실제 수행한 진단

MSVC x64 /O2 독립 진단, 나무 1,100개와 질의 50,000개:

| 방식 | 총 시간 | 충돌 횟수 |
|---|---:|---:|
| 전체 순회 + hypot | 138.764ms | 2,817 |
| 주변 격자 + 제곱 거리 | 0.883ms | 2,817 |

모든 질의에서 결과 일치를 검사했고, 셀 경계·격자 초기화·이동 후 재구성 검사도 통과했다. 이 수치는 충돌 검사만의 합성 부하 측정이며 실제 맵에는 배치 조건을 통과한 나무만 존재한다. 전체 게임 FPS나 GPU 성능 개선량을 의미하지 않는다.

- tests/SceneGraphTests.cpp를 빌드·실행했고 통과했다.
- MSBuild는 로컬 Microsoft SDKs 탐색 경로 접근 제한으로 실행에 실패했다.
- 설치된 MSVC 환경에서 전체 C++ 소스를 /O2 /MD로 직접 컴파일하고 x64 라이브러리와 링크하는 검사는 통과했다. 출력은 임시 폴더 BaseProject-frame-check에 저장했다.
- 게임 창 실행, GLSL 실행 검증, 실제 이동 중 FPS 측정은 하지 않았다.

## 게임에서 확인하는 방법

Visual Studio에서 프로젝트를 다시 로드하고, Release / x64로 빌드하여 기존과 같은 마을·숲 이동 경로를 확인한다. 디버그/릴리스 비교는 같은 구성끼리 해야 한다.

창 제목은 1초마다 다음 값을 갱신한다.

- FPS, frame: 실제 표시 간격의 평균. 60FPS 기준 약 16.7ms.
- max: 해당 구간에서 가장 긴 표시 간격. 평균이 정상이어도 이 값이 자주 커지면 끊김이 생길 수 있다.
- update: 입력·충돌·Actor 갱신의 CPU 시간.
- draw: 도형·UI 생성 및 그래픽 명령 제출 시간. 드라이버 대기도 포함될 수 있다.
- present: 화면 교체 호출 시간. 수직 동기화 및 GPU 대기 등이 포함된다.

이는 CPU 시계 기준이며 별도의 GPU 타이머 측정은 아니다. 마을/숲, 정지/이동 상태의 수치를 비교하면 남은 병목을 좁힐 수 있다. 화면 출력·캐시 최초 생성 직후의 일회성 지연은 지속적인 이동 지연과 구분한다.

## 마을과 사냥터의 비용 차이 — 2026-10-14

사용자 확인: 현재 실행 구성은 **Debug | x64**. 사냥터 진입은 매번 오래 멈추고, 마을로 나올 때는 빠르다. 실제 창 제목의 FPS/update/draw/present 값은 확보하지 못했다.

원인 분석을 위해 현재 소스로 별도 CPU 진단 프로그램을 만들었다. 실제 도형 생성과 Actor/SceneGraph 코드는 유지하고, Renderer의 OpenGL 초기화·명령 제출·후처리·문자 출력은 진단 사본에서 제외했다. 게임 창은 열지 않았다. 측정은 1280×800에서 월드 그리기 준비 비용이며 GPU 처리 시간이나 실제 FPS가 아니다. 게임 코드의 동작은 변경하지 않았다.

### 마을의 낮은 프레임

| 항목 | 마을 시작 지점 | 사냥터 입구 |
|---|---:|---:|
| Debug CPU 월드 그리기 | 16.33ms | 5.16ms |
| 월드 관리 노드 | 10,361 | 4,345 |
| 생성 정점 | 73,959 | 57,249 |

사냥터 입구는 시드 1, 위치 (7, 7). 마을은 기존 고정 배치, 위치 (18, 50). 진단의 마을에는 나무 4,029개, 집 15개, NPC 38명이 있으며 시작 지점의 가시 범위 조건을 통과하는 나무 밑동은 79개였다. 관리 노드 수와 실제 GPU에 보이는 객체 수는 다르다.

가장 큰 CPU 비용은 **마을의 나무·그림자 처리**다. 별도 Debug 비교에서 전체 그리기 16.41ms → 나무 그룹과 그 자식 그림자를 렌더에서 제외하면 3.12ms였다. 해당 그룹은 시작 지점의 정점 약 44,079개, 전체의 약 60%를 만든다. 이 비교는 진단 사본에서만 수행했으며 게임에서 나무를 삭제하거나 숨기지 않았다. 시간 차이는 그래프 수집·정렬과 도형 생성 비용을 함께 포함한다.

확인한 구조적 차이:

- 마을 `DrawTree()`는 줄기·가지·잎 윤곽을 매 프레임 계산하고 삼각형 정점을 다시 만든다. 그림자도 나무마다 만든다. `DrawHouse()`의 집 도형 역시 매 프레임 조합한다.
- 사냥터 `LevelModels`는 모델 정점을 준비해 재사용하고 `Renderer::Model()`에서 복사한다. GPU 정점 업로드까지 영구 캐시된 것은 아니다.
- 마을의 화면 밖 나무는 `SceneGraph::CollectDraw()`에서 먼저 수집·World 정렬 대상에 들어간 다음, 개별 그리기 콜백의 `Visible()` 검사에서 제외된다.
- 사냥터는 `FirstLevel::Draw()`에서 화면 밖 지형 구역을 `SetVisible(false)`로 바꾼다. 그래프 수집이 그 구역과 자식 나무·바위를 일찍 제외한다. 위 시드 1 입구에서 표시 가능한 가지의 노드는 851개였다. 이 중에도 그리기 콜백에서 추가 제외되는 객체가 있다.
- 갱신에서는 두 지역 모두 충돌 세부 단계마다 그래프를 순회한다. 마을의 나무 충돌 격자도 매 프레임 재구성한다. 마을 시작 지점 Debug 진단의 격자 재구성은 약 0.48ms, 그래프 갱신 한 단계는 약 0.54ms로, 측정한 나무 렌더 처리보다 작았다.
- 도형별로 GPU draw call을 한 번씩 호출하는 구조는 아니다. `Renderer::Flush()`가 생성된 정점을 모아서 제출한다. 이번에 확인한 주된 CPU 차이는 제출 전의 도형 생성과 그래프 처리다.

마을 시작 지점의 Release `/O2 /MD` CPU 그리기는 2.18ms였다. Debug `/Od /MDd /D_DEBUG`에서는 최적화가 없고 표준 컨테이너의 디버그 검사 비용도 더해지므로, 마을의 반복 도형 생성 비용이 커진다. 60FPS의 전체 프레임 예산은 약 16.67ms인데 Debug 마을은 CPU 월드 그리기만으로 이 예산에 가깝다. 실제 게임에서는 GPU·후처리·UI·화면 교체 비용이 추가된다.

### 사냥터 진입의 긴 멈춤

입력 콜백에서 `firstLevel.Begin(seed)`를 호출하고, `Begin()`은 매번 `Generate()`와 `BuildScene()`을 실행한다. 나올 때는 `inFirstLevel = false`로 지역 표시를 전환한다. 이 차이가 ‘들어갈 때마다 느리고 나올 때는 빠름’과 일치한다.

`Generate()`는 최대 2,600번 장애물 배치를 시도한다. 배치 후보를 적용할 때마다 `Connected()`가 96×80 타일 맵을 BFS로 탐색하고 전체 바닥 타일 수와 비교한다. 이 작업이 메인 스레드에서 끝나야 다음 화면과 입력을 처리할 수 있다. 모델 캐시는 이 맵 생성과 연결 검사를 생략하지 않는다.

| Debug 진단, 시드 1 | 시간 |
|---|---:|
| 맵 생성 전체 | 3,695.35ms |
| 그중 길 연결 검사 2,183회 | 3,692.39ms |
| Actor/Scene 구성 | 13.33ms |
| 최초 모델 준비 | 5.23ms |

맵 생성 시간의 약 99.9%가 연결 검사였다. 별도로 실제 `Begin()` 전체 경로를 연속 호출했을 때 시드 1은 3.82초, 다음 시드 42는 3.88초였다. 두 번째도 긴 멈춤이 발생하므로 최초 모델 준비만의 문제가 아니다. 진단 환경에서는 모델 캐시 저장이 제한되어 첫 준비 때 메모리에서 모델을 생성했지만, 그 비용도 약 5ms였고 이후 `Load()`는 이미 준비된 메모리 모델을 바로 재사용했다.

Release의 맵 생성은 시드 1·42·930에서 약 277~330ms, `Begin()` 전체는 약 278~301ms였다. Debug가 더 크게 느려지는 작업이지만 Release에도 메인 스레드의 일시 정지가 남는다.

### 개선 우선순위와 검증 경계

1. 성능과 플레이 확인에는 `Release | x64`를 사용한다. Debug는 코드 추적용으로 유지한다.
2. 마을의 정적인 나무·집 도형을 캐시하고, 위치·가림 투명도·흔들림처럼 변하는 값만 갱신한다. Actor/SceneGraph 소유권은 유지한다.
3. 마을도 구역 단위로 묶어 화면 밖 객체를 그리기 수집·정렬 전에 제외한다. 렌더 제외로 NPC 시뮬레이션이나 충돌 규칙을 임의로 중단하지 않는다.
4. 맵 연결성을 유지하면서 장애물마다 수행하는 전체 BFS를 줄인다. 검증된 지역 검사로 충분한 후보는 전체 탐색을 생략하거나, 연결성이 보장되는 생성 방식으로 바꾸고 최종 검사를 수행하는 방향을 검토한다.
5. 생성 작업을 프레임에 나누거나 타일·스폰 데이터 생성만 별도 작업으로 옮겨 화면·입력의 정지를 줄인다. Actor 그래프의 변경은 게임 스레드에서 처리한다. 재입장 때 기존 맵을 재사용하면 생성 비용을 없앨 수 있지만, 현재 매번 새 맵과 몹을 만드는 동작이 달라지므로 별도 결정이 필요하다.

이번 요청에서는 원인 진단과 기록만 수행했다. 실제 게임 실행 파일 빌드·플레이, GPU 타이머 및 실제 FPS 측정, 위 최적화의 구현은 수행하지 않았다. 진단 실행 파일과 원시 결과는 임시 폴더 `BaseProject_SE_cost_probe`에 저장했다.

## 최적화 적용과 독립 검증 — 2026-10-14

위 원인 진단 이후 다음 변경을 적용했다.

- 마을의 집 본체, 나무 줄기·잎 층, 그림자 정점을 최초 표시 때 메모리에 저장해 Renderer::Model()로 재사용한다. 나무 흔들림·플레이어 가림 투명도와 굴뚝 연기는 매 프레임 갱신한다. 나무 위치·크기·종류가 바뀌면 해당 모델을 다시 만든다. 이번 캐시는 실행 중 메모리 캐시이며 기존 사냥터의 파일 모델 캐시와 별개다.
- 나무를 16×16 월드 단위의 구역 Actor 아래에 배치한다. 현재 Actor 위치로 구역 범위를 갱신하고, 화면 밖 구역과 개별 집·나무를 수집·정렬 전에 제외한다. Actor::SetDrawCull()은 그리기만 제어하므로 화면 밖 NPC 갱신이나 충돌 규칙을 바꾸지 않는다.
- 캐시 정점은 벡터에 일괄 복사한 뒤 연속 메모리에서 위치·색상·알파를 적용한다. Debug에서 정점마다 반복되던 벡터 반복자 검사와 push_back() 비용을 줄였다.
- 장애물 배치 시 제거된 칸의 네 이웃이 계속 연결되는지 검사한다. 주변 8칸 안에서 연결을 확인할 수 있으면 즉시 끝내고, 그렇지 않으면 이웃들을 연결할 때까지만 BFS를 수행한다. 이미 연결된 맵에서 내부 칸 하나를 제거한다는 생성 규칙을 이용하며, 길을 끊는 후보는 기존처럼 취소한다. 진입마다 새 맵을 만드는 동작과 난수·몹 배치 규칙을 유지한다.

Debug 변경 전 값은 최종 변경 직전에 기존 진단 실행 파일을 다시 실행한 결과다. 최초 진단의 16.33ms/약 3.8초와 차이가 있어 실행 시점에 따른 변동을 그대로 기록했다. Release 변경 전 값은 앞선 원인 진단 값이다. 생성 시간과 진입 시간은 별도 생성 호출의 측정이므로 단순 합산하거나 서로의 부분 시간으로 해석하지 않는다.

마을 시작 지점의 정점은 변경 전후 73,959개, 호숫가는 Debug 85,095개/Release 84,849개로 같았다. 나무 4,029개·집 15개·NPC 38명도 유지된다. 월드 노드는 구역 Actor 321개 추가로 10,361 → 10,682개가 됐지만, 화면 밖 구역의 자식들을 렌더 수집에서 제외한다. Debug 충돌 격자와 구역 범위 재구성은 최종 약 0.54ms, 그래프 갱신 한 단계는 약 0.40ms였다.

### 수행한 검사와 남은 확인

- 변경 전 FirstLevel 사본과 최종 구현에서 32개 시드의 전체 타일, 마지막 난수 상태, 192개 몹의 위치·종류·체력을 비교해 모두 일치했다.
- 시드 1·42·930의 모든 바닥 칸을 하나씩 막아 새 연결 검사와 기존 전체 BFS 판정을 비교했다. 야영지 칸은 생성 규칙상 제거 대상이 아니므로 제외했다. 최종 맵의 전체 연결성 검사도 통과했다.
- 기존 그리기 함수와 캐시 경로의 정점 수·위치·색상·알파·머티리얼·UV를 비교했다. 소나무/활엽수, 세 크기, 여러 시간·카메라, 플레이어 가림, 나무 위치·크기·종류 변경, 15채 집의 연기, 움직인 그림자를 검사했다. 화면 좌표 오차 허용치 0.004픽셀 내에서 일치했다.
- 중첩 모델 캡처가 기존 프레임 정점을 보존하고 그리기 오프셋을 한 번만 적용하는지 확인했다. 구역 밖으로 이동한 나무·부모 Actor의 범위 갱신, 그리기 제외 중 업데이트·표시 상태 유지 검사도 통과했다.
- 실제 C++ 소스로 Debug 독립 테스트를 컴파일·링크하여 SceneGraphTests, TreeCollisionGridTests, LevelExpansionTests, TutorialPopulationTests를 실행했다. Actor 이동·수명, 50,000개 충돌 비교, 38 NPC/35 이동 패턴, 몹 4종 처치·전리품 획득·재등장 검사를 통과했다.
- C++ 정적 컴파일과 변경 내역 공백 검사를 수행했다. 게임 실행 파일의 Visual Studio 빌드, OpenGL/셰이더 실행, 실제 플레이와 최소 FPS는 확인하지 않았다.

독립 진단·비교 프로그램과 원시 결과는 %TEMP%\BaseProject_SE_optimization에 저장했다. baseline은 변경 전 소스, Release\ConnectivityRegression.txt·GeometryRegression.txt는 비교 검사 결과, 각 구성의 results-candidate-*-final.txt는 최종 측정이다. 모델 최초 생성은 메모리에서 수행됐고, 진단 환경의 캐시 파일 저장 제한 메시지는 위 CPU 시간에 포함된다.

게임에서는 같은 구성으로 마을·호숫가 이동, 나무의 흔들림과 가림 전환, 집 연기·그림자, 출입구 E 진입/귀환을 여러 번 확인한다. 성능과 플레이 확인에는 Release | x64를 권장한다. 위 수치는 10월 14일 구조의 CPU 도형 준비 비용이며, 이후 추가된 외곽 장식과 지역의 실제 FPS 측정값이 아니다. GPU·후처리·글자·화면 교체를 포함하는 실제 FPS나 최저 30FPS를 보장하지 않는다.
